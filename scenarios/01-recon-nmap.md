# Scenario 01: Reconnaissance - Nmap Scan

## Objective
Perform network service discovery against the target to identify open ports and running services, evaluate Wazuh's default detection capability for reconnaissance activity, and attempt to close the detection gap through custom rule development.

## MITRE ATT&CK Mapping
- **Technique**: T1046 - Network Service Discovery
- **Tactic**: Discovery

## Environment
- **Attacker**: Kali Linux (192.168.1.11)
- **Target**: DVWA-target (192.168.1.10), running DVWA via Docker
- **Monitoring**: Wazuh Server (wazuh-server)

## Part 1: Baseline Test (Default Wazuh Configuration)

### Attack Command
```bash
nmap -sV -A 192.168.1.10
```

### Detection Result
- **Alert triggered**: No
- **Finding**: Default Wazuh ruleset does not include detection logic for TCP port scanning, as expected for a host-based IDS relying on log sources rather than raw network traffic inspection.

## Part 2: Custom Detection Attempt (auditd + Wazuh Custom Rule)

To close this detection gap, a custom detection pipeline was attempted using Linux `auditd` as an additional log source for Wazuh.

### Setup Steps
```bash
# Install and enable auditd on target
sudo apt-get install -y auditd
sudo systemctl enable --now auditd

# Add audit rule to monitor connect/accept syscalls
sudo auditctl -a always,exit -F arch=b64 -S connect -S accept -k network_connections

# Configure Wazuh agent to read audit log
sudo tee -a /var/ossec/etc/ossec.conf << 'EOF'
<localfile>
  <log_format>audit</log_format>
  <location>/var/log/audit/audit.log</location>
</localfile>
EOF
sudo /var/ossec/bin/wazuh-control restart
```

### Custom Rule Iterations (Wazuh Server)
Two iterations of custom rules were developed in `local_rules.xml`:

**Iteration 1:**
```xml
<group name="custom,recon,">
  <rule id="100100" level="7">
    <decoded_as>auditd</decoded_as>
    <description>Possible network connection detected via auditd monitoring - potential port scan</description>
    <mitre>
      <id>T1046</id>
    </mitre>
  </rule>
</group>
```
Result: Too generic — matched by Wazuh's built-in rule 80700 ("Audit: Messages grouped", level 0) before reaching the custom rule.

**Iteration 2:**
```xml
<group name="custom,recon,">
  <rule id="100100" level="7">
    <if_sid>80700</if_sid>
    <field name="audit.type">SYSCALL</field>
    <description>Possible network connection detected via auditd monitoring - potential port scan</description>
    <mitre>
      <id>T1046</id>
    </mitre>
  </rule>
</group>
```
Result: Rule did not trigger on live testing despite confirmed SYSCALL events present in `audit.log`.

### Investigation Findings
1. Confirmed via `wazuh-logtest` that Wazuh correctly decodes auditd log format (`name: 'auditd'`, `audit.type: 'PROCTITLE'`/`'SYSCALL'`).
2. Confirmed via direct log inspection (`grep "type=SYSCALL" audit.log`) that syscall events were being captured, including from `apache2` process with `key="network_connections"`.
3. However, closer inspection revealed the captured `connect`/`accept` events were predominantly **local Unix domain socket traffic** (`saddr_fam=local`, paths like `/var/run/nscd/socket`, `/dev/log`) generated by routine system activity (PAM authentication, systemd internals, `sudo` usage) — not external network connections from the Nmap scan.
4. Nmap's default SYN scan (`-sS`) does not complete a full TCP handshake, meaning it may not trigger an `accept()` call at the application layer at all, regardless of audit rule scope.

## Analysis
This scenario produced a two-part finding. First, it confirmed the expected architectural limitation of Wazuh as a host-based IDS: without additional log sources, network-level reconnaissance (port scanning) generates zero alerts by default.

Second, and more substantively, an attempt to close this gap via `auditd` integration surfaced a deeper, more nuanced limitation: **the audit rule configured to monitor network connections (`-S connect,accept`) was too broad in scope**, capturing high-volume local Unix domain socket activity that drowned out any signal from the actual external scan. This is a realistic and common pitfall in SIEM tuning — overly broad data collection rules create noise that obscures the actual detection target, even when the underlying pipeline (auditd → Wazuh decoding → rule matching) is functioning correctly end-to-end.

Resolving this would require filtering the audit rule specifically by socket address family (e.g., excluding `saddr_fam=local`, retaining only `saddr_fam=inet`/`inet6`), and additionally testing with a full TCP connect scan (`nmap -sT`) rather than the default SYN scan, to guarantee application-layer `accept()` calls are triggered.

## Severity Classification
**Low** — reconnaissance activity alone (pre-exploitation, no indication of compromise), consistent with the Low criteria in the project severity matrix.

## Recommendation
1. Do not rely on Wazuh's default configuration for network scan detection — this is a known architectural limitation, not a misconfiguration.
2. If pursuing auditd-based detection further, scope the audit rule to `saddr_fam=inet` explicitly, rather than monitoring all connect/accept syscalls indiscriminately.
3. Consider a dedicated NIDS/NDR tool (Suricata or Zeek) as a more purpose-built alternative to auditd for network-layer detection, feeding alerts into Wazuh for unified visibility.
4. This finding — and the iterative troubleshooting process behind it — is documented as a key architectural insight and a **future work item**, rather than a resolved detection capability.
